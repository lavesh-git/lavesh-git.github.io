# 1.3.5 Celebrity Problem

The **celebrity problem** (or hot key problem) in system design occurs when a single user with millions of followers generates a disproportionate amount of read/write traffic. This overloads a single database partition or cache node, causing severe performance degradation or system crashes while the rest of the cluster sits idle. \[[1](<https://medium.com/towardsdev/the-celebrity-problem-how-one-viral-post-breaks-sharded-databases-and-how-rust-helped-prove-it-ade26571f140>), [2](<https://x.com/adityatandon02/status/2051908139247861970>), [3](<https://www.linkedin.com/pulse/celebrity-problem-distributed-systems-a-s-md-ferdousul-haque-k093c>), [4](<https://www.youtube.com/shorts/xELOftQqSLM>)\]

Core Issues

- **Hot Partitions:** Sharded databases route data using keys like user_id % N. A celebrity's high-traffic ID maps to one specific shard, exhausting its CPU and memory.

- **Write/Read Amplification (Fan-Out):** Pushing a post to millions of follower timelines at write-time freezes the system.

- **Like/Comment Floods:** Millions of concurrent requests hitting a single counter or post ID cause database throttling. \[[1](<https://www.youtube.com/watch?v=ZH9JzLEhfyE>), [2](<https://designgurus.substack.com/p/system-design-basics-handling-hot>), [3](<https://www.linkedin.com/posts/satyanand-deva-0a313294_dynamodb-systemdesign-scalability-activity-7375212283402256384-ZiXO>), [4](<https://www.linkedin.com/pulse/celebrity-problem-distributed-systems-a-s-md-ferdousul-haque-k093c>), [5](<https://medium.com/towardsdev/the-celebrity-problem-how-one-viral-post-breaks-sharded-databases-and-how-rust-helped-prove-it-ade26571f140>)\]

Mitigation Strategies

- **Hybrid Fan-Out Models:** Use "Fan-out on write" (Push) for normal users whose feeds update instantly, and switch to "Fan-out on read" (Pull) for celebrities. Fetch celebrity posts on-demand and merge them dynamically when a fan opens their app. \[[1](<https://www.youtube.com/watch?v=ZH9JzLEhfyE>), [2](<https://designgurus.substack.com/p/system-design-basics-handling-hot>)\]

- **Caching Layers:** Place distributed caches like Redis in front of the database to absorb read-heavy timeline requests. \[[1](<https://www.youtube.com/shorts/cFhAZPZl_CY>), [2](<https://www.youtube.com/shorts/xELOftQqSLM>)\]

- **Write Sharding (Random Suffixes):** Split high-contention counters or write keys by appending a random integer suffix (e.g., postId#1, postId#2) and aggregate the read results later. \[[1](<https://www.linkedin.com/posts/satyanand-deva-0a313294_dynamodb-systemdesign-scalability-activity-7375212283402256384-ZiXO>), [2](<https://www.youtube.com/shorts/cFhAZPZl_CY>)\]

- **Dedicated Partitions:** Isolate viral or celebrity entities onto specialized hardware shards with extra read replicas. \[[1](<https://designgurus.substack.com/p/system-design-basics-handling-hot>), [2](<https://www.youtube.com/shorts/cFhAZPZl_CY>)\]
